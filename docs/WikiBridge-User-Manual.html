About This Manual

This manual is the complete, self-contained documentation of WikiBridge. It is written for three audiences at once: end users who drive the tool from the command line or from a GUI backed by the HTTP API; administrators who configure authentication against corporate identity providers and schedule imports; and developers who embed WikiBridge as a Python library, write new source adapters, or integrate agents through the skill layer.

Every public module, class, function and method of the code base is documented here, including each parameter, its type, its default and its behaviour, along with the private helpers that matter for understanding the system. Procedures ("how do I…") are collected in Part II; exhaustive references follow in Parts III–VII.

Part I — Getting Started

1.1 What WikiBridge is

WikiBridge turns scattered knowledge — corporate wikis, documentation sites, Notion workspaces, folders of PDF and Office documents — into a local, project-scoped “LLM Wiki”: a tree of plain Markdown pages with YAML frontmatter, a SQLite FTS5 full-text index, and an automatically generated knowledge graph. The result is a self-contained corpus that a human can browse with any editor and that an LLM agent can consume as retrieval context (a local RAG), without any external service.

The pipeline has four stages, each usable on its own:

  1. Acquire — source adapters download content from MediaWiki, Confluence, Notion, or any HTML site (generic crawler); a separate ingest path converts local documents (PDF, DOCX, PPTX, XLSX, HTML, CSV, EPUB…) with markitdown.
  2. Normalise — everything becomes Markdown with rich frontmatter (url, revision, content_sha256), enabling deduplication and incremental synchronisation.
  3. Catalogue — an LLM “brain” (LM Studio over an OpenAI-compatible endpoint, or the hosting agent itself) extracts entities, concepts and relations from every page and writes them as first-class wiki pages with backlinks.
  4. Serve — a Flask HTTP API (default 127.0.0.1:8775) exposes all operations to GUIs; a skill layer exposes them to coding agents.

Authentication against protected sources is a first-class concern: WikiBridge stores reusable auth profiles (bearer, basic, header, cookie, OAuth 2.0) and, for corporate SSO, performs a full browser-based OAuth 2.0 Authorization Code + PKCE login, persists the tokens, refreshes them silently, auto-selects the right profile per host, and detects “login walls” during a crawl so that protected pages are never silently saved as access denied boilerplate.

1.3 Installation

Requirements

  • Python ≥ 3.10 (Windows, WSL or Linux).
  • git (only for the optional skill ensure-llmwiki installer).
  • Optionally LM Studio (or any OpenAI-compatible endpoint) for automatic cataloguing.

Install from the repository

cd C:\Projects\wikibridge
python -m venv .venv
.venv\Scripts\activate          # Linux/WSL: source .venv/bin/activate
pip install -e .                # or: pip install -r requirements.txt

The editable install registers the wikibridge console script (entry point wikibridge.cli:main). Dependencies: requests, beautifulsoup4, markdownify, trafilatura, markitdown, flask, flask-cors, python-slugify, pyyaml, browser-cookie3 (SSO cookie capture).

Tip — WikiBridge computes all data paths from the package location, so the CLI, the HTTP server and the agent skill see the same data whether launched from Windows (C:\Projects\wikibridge) or from WSL (/mnt/c/Projects/wikibridge).

1.4 Ten-minute quick start

# 1. create a project and make it active
wikibridge project create "Product Docs" --description "Vendor documentation"

# 2. import a public documentation site, 1 level deep
wikibridge import https://docs.example.com/guide --depth 1 --scope subtree

# 3. drop a folder of PDFs into the same project
wikibridge ingest "D:\specs" --recursive

# 4. search everything you just captured
wikibridge search "rate limiting"

# 5. regenerate the knowledge graph and open it
wikibridge graph
#   → data/projects/product-docs/graph/graph.html

For a wiki protected by corporate SSO, add two commands before the import — the rest is automatic (see §2.3):

wikibridge auth detect https://wiki.corp.example/Home --save corp
wikibridge auth login corp          # browser opens; log in once
wikibridge import https://wiki.corp.example/Home --depth 2

Part II — User Guide (Procedures)

2.1 Working with projects

All knowledge in WikiBridge is isolated per project. A project is identified by a slug (lower-case, digits and dashes, derived automatically from the name) and owns its own wiki tree, FTS index, import history, graph and pending catalogue queue. One project is active at any time; every command operates on the active project unless you pass the global --project <slug> option.

Procedure — create, switch, list, delete

wikibridge project create "ACME Rollout" --description "2026 rollout knowledge"
wikibridge project list          # JSON list; "active": true marks the current one
wikibridge project switch acme-rollout
wikibridge project delete old-project
  • create fails with an error if the slug already exists. The slug of "ACME Rollout" is acme-rollout.
  • delete removes the project from the registry only; files on disk are preserved and must be removed manually (a deliberate safety choice). The default project cannot be deleted.
  • If no project exists yet, the first command that needs one auto-creates default.

2.2 Importing an external wiki

An import is a resumable job: it resolves a seed set from your URL, walks links breadth-first within the same wiki, converts every page to Markdown and records the job in imports.json. The three knobs that shape an import are adapter, scope and depth; everything else is guarded by limits (§3).

2.2.1 Choosing the adapter

--adapter auto (default) sniffs the URL: Notion hosts first, then Confluence URL patterns, then a MediaWiki api.php probe; anything else falls back to the generic HTML crawler. Force a specific adapter with --adapter generic|mediawiki|confluence|notion when sniffing guesses wrong (e.g. a MediaWiki behind a non-standard path).

2.2.3 Procedure — a typical guided import

# preview scale first: keep limits tight
wikibridge import https://wiki.example/Category:API \
    --scope subtree --depth 1 --max-pages 50 \
    --include "API*" --exclude "*Deprecated*"

# happy with the result? raise the caps and resume:
#   truncated jobs keep their frontier and can be re-run
  • --include/--exclude take shell-style globs matched against page titles (or URL when a title is missing). Repeat the option to add patterns; exclude wins.
  • --no-catalog skips LLM cataloguing for this run (you can drain later, §2.6).
  • The command prints live progress ([fetching] 12/50 Page title…) and a final JSON summary with id, state, pages, skipped, truncated, errors. Exit code 0 only when state="done".
Note — a page that fails to download or convert never aborts the job; it is recorded in errors and counted in skipped. Whole-job aborts happen only for global conditions: total-size budget, wall-clock limit, cancellation, or an authentication wall (§2.3.6).

2.2.4 What lands on disk

Every page becomes wiki/sources/<slug>.md with frontmatter: title, kind: web, url, import_id, revision, content_sha256, updated, adapter. Identical content (same SHA-256) is never rewritten — this powers incremental sync. The FTS index is updated per page and index.md is regenerated at job end.

2.3 Authentication: from static tokens to corporate OAuth/SSO

Auth is expressed as named, reusable profiles stored in secrets/auth_profiles.json. Adapters never see credentials: a profile is applied to the shared HTTP session (header, basic auth pair, cookies…) before any request is made.

Every profile may also carry hosts: ["wiki.corp.example", …] — the list of wiki hosts it authenticates. This is what makes profile selection automatic (§2.3.5).

2.3.2 The env: indirection

Any credential field may hold the literal string env:VARIABLE_NAME instead of the secret itself. The value is then resolved from the environment at use time and the secret never touches the disk. If the variable is unset at runtime the operation fails with "variabile d'ambiente mancante".

{"type": "basic", "username": "svc-wiki@corp.example",
 "password": "env:WIKI_API_TOKEN", "hosts": ["wiki.corp.example"]}

Recognised IdPs with ready-made presets: Azure AD / Entra ID (tenant extracted from the redirect; OIDC issuer), Google (Desktop-app flow, access_type=offline), Atlassian Cloud (3LO endpoints, Confluence read scopes, audience=api.atlassian.com), Okta and Auth0 (issuer = redirect host). Each preset includes a note telling the administrator what kind of app registration is required and which redirect URI to register: http://127.0.0.1:8776/callback.

2.3.4 Procedure — interactive browser login (OAuth 2.0 + PKCE)

wikibridge auth login corp              # opens the system browser
wikibridge auth login corp --no-browser # print the URL instead (SSH, kiosk)
  1. WikiBridge builds an Authorization-Code-with-PKCE request (S256 challenge, random state) and starts a loopback listener on http://127.0.0.1:<redirect_port>/callback (default port 8776).
  2. Your browser opens the IdP's login page; you authenticate normally — MFA, conditional access, smart cards all work because it is a real browser session.
  3. The IdP redirects to the loopback listener; WikiBridge validates state, exchanges the code for tokens (adding client_secret only if the profile has one — public clients need none thanks to PKCE), and stores access + refresh token in secrets/.tokens.json.
  4. The command reports whether a refresh token was granted. If not, add the offline_access scope (or access_type=offline for Google) so future renewals are silent.

Endpoints are found in this order: explicit auth_url/token_url in the profile → OIDC discovery on issuer (/.well-known/openid-configuration). The login times out after auth_login_timeout_s (default 300 s).

2.3.5 What happens afterwards — the automatic path

  • Profile selection by host. import/sync/refresh pick the profile whose hosts matches the URL host (exact or subdomain suffix) — no --auth-profile needed. Passing --auth-profile explicitly binds that host to the profile for next time.
  • Silent renewal. A cached access token is reused until ~60 s before expiry, then renewed with the refresh token. Rotating refresh tokens (Azure AD, Atlassian) are handled: the newest one always replaces the cached one.
  • Interactive fallback. If renewal fails (revoked/expired refresh token) and auth_interactive is true (default), the browser login starts again by itself. Set auth_interactive: false (or WIKIBRIDGE_AUTH_INTERACTIVE=0) on headless machines: the operation then fails fast with the exact auth login command to run.

2.3.6 Login walls during a crawl

While a job runs, the HTTP session inspects every response for an authentication wall: HTTP 401; HTTP 403 with a WWW-Authenticate challenge; a redirect that lands on a known IdP host; or an HTML login form (password field on a login-looking URL) served in place of content. When detected:

  1. the job attempts one automatic re-login (max 2 per job) — token refresh or browser round-trip — and retries the page;
  2. if re-login is impossible (no profile, headless, still walled) the job stops in state auth_required, keeps the not-yet-visited pages in its frontier, and prints the recovery hint. After wikibridge auth login <profile> the same job resumes from where it stopped.
Known issue — in release 0.1, on anonymous imports of public sites the wall detector can trigger on the site's own “Log in” page reached by the crawler and abort the job; see Part VIII, issue #2, for the workaround (--exclude the login page).

2.3.7 Procedure — SSO without OAuth (cookie capture)

Many intranets only offer a browser SSO form (SAML behind the scenes) and no OAuth client registration. Use a cookie profile:

wikibridge auth detect https://intranet.corp.example --save intranet   # kind: sso_form
wikibridge auth login intranet
  1. The browser opens on login_url; complete the SSO login as usual.
  2. Press Enter in the terminal. WikiBridge reads the session cookies for the domain directly from your browser's cookie store (Firefox, then Edge, Chrome, Chromium — via browser-cookie3) and saves them in Mozilla cookies.txt format under secrets/cookies/<profile>.txt.
  3. If no browser store is readable (e.g. Chrome's encrypted store without the right keys), WikiBridge falls back to asking you to paste the Cookie: header manually (copy it from DevTools ▸ Network).
Note — session cookies expire on the IdP's schedule; when they do, the next import stops in auth_required and a new auth login refreshes the capture.

2.4 Ingesting local documents

wikibridge ingest "D:\contracts\msa-2026.pdf"
wikibridge ingest "D:\specs" --recursive --no-catalog
  • Supported via markitdown: .pdf .docx .pptx .xlsx .xls .html .htm .csv .json .xml .epub .msg; passed through as-is: .md .markdown .txt .rst. Anything else in a directory scan is silently ignored; a single unsupported file raises an error.
  • Per-file cap 50 MB; oversized, unconvertible or empty-conversion files are skipped and listed in errors (exit code 1 if any).
  • Each document becomes a source with kind: document, url: file:///…, original_path and format in frontmatter; content SHA-256 dedup applies, so re-ingesting an unchanged folder is a no-op.
  • The file or folder is registered as an updatable source (ingests.json): wikibridge update later re-checks it, rewrites changed documents in place, follows renames and removes files that disappeared (§9.6).
  • --permissions (Windows) also reads each file's NTFS permissions and applies them as access rules in multi-user mode (§9.5).

2.5 Searching, indexing, browsing

wikibridge search "sso token rotation" --limit 10
wikibridge index          # full FTS rebuild + regenerate index.md
  • Search is SQLite FTS5 with BM25 ranking and **bold** snippet highlighting; diacritics are folded (unicode61 remove_diacritics 2). Free-form input is safe: every term is internally quoted, so dashes/colons never break the query syntax.
  • The index updates incrementally after every import/ingest/catalogue write; wikibridge index is only needed after hand-editing pages on disk.
  • Browse the wiki with any Markdown tool: start from wiki/index.md (all pages, by section) or wiki/log.md (chronological audit trail).

2.6 LLM cataloguing and the knowledge graph

The cataloguer reads every new source, splits it into ~10 000-character chunks on paragraph boundaries, asks the brain for structured JSON (entities, concepts, relations), merges partial results by normalised name, and writes/updates pages under entities/ and concepts/ with a “Menzioni” (mentions) backlink section. Relations are appended to graph/relations.jsonl.

The three brain modes (brain_mode)

ModeWho is the LLMWhen work happens
openai_httpLM Studio or any OpenAI-compatible endpoint (lmstudio_url)inline during import/ingest, or on demand via catalog-drain
agentthe hosting agent itself (Claude Code, Hermes…)tasks are queued in _pending/; the agent drains them with catalog-apply
nonenobodynever — imports and FTS still work fully

Procedures

# drain the queue with LM Studio (also used by the GUI button)
wikibridge catalog-drain

# agent mode: apply one prepared result
wikibridge catalog-apply sources/payment-api.md \
    --json '{"entities":[…],"concepts":[…],"relations":[…]}'

# rebuild the graph after cataloguing
wikibridge graph

wikibridge graph writes graph/graph.json (nodes = wiki pages, coloured by section; edges = mentions + catalogued relations) and a self-contained graph/graph.html viewer (vis-network from CDN, dark theme) — double-click to explore, no build step.

2.7 Keeping content fresh: sync and refresh

wikibridge sync imp-0003        # re-check every page of one import job
wikibridge refresh sources/payment-api.md   # re-fetch a single page
  • sync asks the adapter changed_since(revision) for each page of the job and re-downloads only pages whose revision moved (MediaWiki revid, Confluence version, Notion last_edited_time, HTTP ETag/Last-Modified). Unchanged bodies (same SHA-256) are not rewritten.
  • refresh re-fetches one page using the origin URL and adapter recorded in its frontmatter, re-using the original import's auth profile (or the host-matched one).
  • Both honour the same auth machinery as imports, including silent token renewal and the auth_required stop (CLI exit code 2 with a JSON error).
  • update is the general form: wikibridge update checks every wiki branch, folder and file of the project (or only those selected with --import, --ingest, --path), finds new and removed pages, and never duplicates a page. sync <id> is equivalent to update --import <id>. See §9.6.

2.8 Running the HTTP server / GUI backend

wikibridge serve       # Flask on http://127.0.0.1:8775
  • Meant for a local GUI (e.g. a Control Center “Knowledge” tab). CORS is enabled; optional bearer auth by setting api_auth_token in config.json (empty = no auth, loopback only — do not expose beyond localhost without a token and a reverse proxy).
  • One job at a time: import/ingest/sync requests return 202 and run in a background thread; a second concurrent job request gets 409. Poll GET /health or GET /imports for live progress (phase, pages, detail).
  • Auth profiles over HTTP are write-only: the GET endpoint returns names, types and hosts, never secrets.
  • Interactive logins can be driven from the GUI: POST /auth/login opens the browser on the server's machine (they are the same machine in the intended setup) and GET /auth/login/status reports the outcome; for cookie profiles call POST /auth/login once to open the browser, then again with {"capture": true} after finishing the SSO login (see Part VIII, issue #8, for release-0.1 caveats).
  • For unattended operation prefer auth_interactive: false so background jobs never block waiting for a browser (Part VIII, issues #4/#9).

Autostart on Windows: add a HKCU\…\Run key or a Task Scheduler entry that launches wikibridge serve in the venv.

2.9 Agent integration (skill layer)

The repository ships a skill/ directory (trigger /wiki-import) so coding agents can drive WikiBridge without the venv:

python3 /mnt/c/Projects/wikibridge/skill/wikibridgectl.py <command> […]
  • wikibridgectl.py forwards any CLI command, adds status (compact JSON: active project, last imports, pending catalogue tasks) and ensure-llmwiki (installs the companion llm-wiki reading skill on Hermes/WSL, OpenClaw and Claude Code runtimes — idempotent).
  • In skill context the recommended brain mode is agent: after every import the agent reads each task in _pending/, applies the prompt in skill/prompts/catalog_page.md to the source, and posts the JSON back with catalog-apply — the agent itself is the cataloguing LLM, no external API calls.
  • Knowledge answering rule: agents should read wiki/index.md first, then open linked pages, use search for pinpoint queries, and never mix knowledge across projects.

Part III — Configuration Reference

Configuration is a three-layer cascade, applied in order: dataclass defaults → config.json (repository root) → environment variables WIKIBRIDGE_<FIELD_UPPERCASE>. Environment values are coerced to the field's type (booleans accept 1/true/yes, case-insensitive). An invalid config.json aborts startup with a clear message.

# config.json example
{
  "api_port": 8775,
  "brain_mode": "agent",
  "max_pages": 500,
  "auth_interactive": false

Part V — HTTP API Reference

Base URL http://127.0.0.1:8775 (configurable). All bodies are JSON unless stated; all responses are JSON. When api_auth_token is set, send Authorization: Bearer <token> on every request (401 otherwise; CORS pre-flight OPTIONS is exempt). Endpoints that accept a project parameter read it from the query string, the JSON body or the form field, in that order; omitted = active project.

Job model. Import, ingest and sync run in a single background slot. Starting one returns 202 {"started": true}; if the slot is busy you get 409 {"error": "un altro job è in corso"}. The current job's live state (running, kind, phase, pages, max_pages, detail, error, result) is embedded in GET /health and GET /imports.

6.7.1 adapters.base — the contract

PageRefdataclass

A page to visit: id (adapter-native identifier — MediaWiki title, Confluence content id, Notion page id, or the URL itself), url, title="", depth=0 (BFS distance from the seed).

PageContentdataclass

SourceAdapter(session, limits)abstract class

Every adapter receives the shared ThrottledSession and the job's ImportLimits; it must never bypass either.

  • detect(url, session) → bool classmethod — cheap sniffing: “does this URL belong to my wiki type?”. Base returns False.
  • resolve(url, scope) → list[PageRef] abstract — builds the seed set for page|subtree|space and initialises adapter state (API endpoint, scope prefix…). Must be called before fetch.
  • fetch(ref) → PageContent abstract — downloads and converts one page.
  • changed_since(ref, revision) → bool — return False only when the page provably did not change; base implementation returns True (always re-fetch).

6.7.3 adapters.generic — universal HTML crawler

GenericAdapterclass

For GitHub wikis, GitBook, DokuWiki, documentation sites — anything without a usable API. Skips binary/static extensions (_SKIP_EXT: images, archives, media, css/js…). JavaScript-rendered pages are not supported (no headless browser in 0.1).

  • resolve(url, scope) — seed is always just the URL; scope shapes the crawl fence: page → same host; subtree → same host + path prefix of the seed's directory; space → whole host. Returns [PageRef(depth=0)].
  • _in_scope(url) → bool helper — host match + extension filter + path-prefix check; applied to every extracted link.
  • _allowed_by_robots(url) → bool helper — per-host cached robots.txt (fetched through the throttled session; unreachable/non-200 = allow) matched against the configured User-Agent. Disabled by limits.respect_robots=False.
  • fetch(ref) — robots check (raises PermissionError when disallowed), GET, raise_for_status(), content-type must contain html/xml (raises ValueError), size cap, then html_to_markdown; links via extract_links filtered by _in_scope; revision = ETag or Last-Modified.
  • changed_since(ref, revision) — HEAD request compared against the stored validator; any failure → True (re-fetch).

MediaWikiAdapterclass

Speaks to api.php (candidates probed: /w/api.php, /api.php, /mediawiki/api.php). Every call sends maxlag=5 (wiki etiquette); 429/5xx are retried by the session.

  • detect(url, session) classmethod — URL must look like a wiki path (/wiki/… or index.php?title=…) and a candidate api.php must answer a siteinfo query.
  • _ensure_api(url) / _call(**params) helpers — endpoint discovery with caching (raises RuntimeError when no api.php answers) and JSON call wrapper that surfaces MediaWiki-level errors (raises RuntimeError with the API's info message).

8.2 Known issues in release 0.1

An independent multi-agent code review of the authentication subsystem confirmed the following defects, kept here for transparency until fixed. Numbers match the internal review report.

#AreaIssue & practical workaround
1Token cacheA refresh token supplied via env:VAR is persisted resolved (plaintext) into .tokens.json after the first refresh. Workaround: rely on interactive login instead of a pre-seeded env refresh token, or protect/purge .tokens.json.
2Wall detectorAnonymous imports of public sites can abort in auth_required when the crawler follows the site's own “Log in” link. Workaround: --exclude "*login*" (and similar) or import with --scope subtree away from the login page.
3AdaptersConfluence/MediaWiki endpoint probes swallow the wall error, misreporting an expired session as “REST API not found” / wrong adapter. Workaround: run auth login first, then import.
4Headless refreshWith auth_interactive left true, an expired refresh token in an unattended job blocks up to 5 min waiting for a browser nobody drives, then ends in error (not auth_required). Workaround: set auth_interactive: false on servers.
5Import retryIf a page is still walled after a “successful” re-login, it is silently skipped (absent from frontier and index). Workaround: verify pages count; re-import after fixing auth.
6SyncA failure on the single retried page aborts the whole sync run and skips persisting its record. Workaround: re-run sync; check errors.
7Re-login budgetPer-page 401s (permission-restricted pages) consume the 2-re-login budget and can abort an otherwise valid job. Workaround: --exclude restricted areas.
8Server cookie loginPOST /auth/login for cookie profiles captures immediately (pre-login cookies) unless you use the two-phase capture:true call after logging in. Prefer the CLI flow for cookie profiles.
9Server cookie re-loginA cookie re-login triggered inside a server job can block on a console prompt when the server has a TTY. Workaround: auth_interactive: false for served instances.
10Login concurrency/auth/login state is not lock-protected; concurrent logins can misreport status. Workaround: serialise logins from the GUI.

8.3 Design limits (by intent)

  • Depth hard-capped at 3; one background job at a time over HTTP; attachments not downloaded (max_attachments_mb=0).
  • JavaScript-rendered pages unsupported (no headless browser).
  • project delete never deletes files; auth secrets are write-only over HTTP; page reads are confined to the wiki tree (path-traversal guard).
  • The Flask development server targets loopback GUIs — front it with a real WSGI server + TLS if it must leave the machine.

Part IX — Multi-User Access Control (Enterprise)

By default WikiBridge is a single-user tool: whoever reaches the API sees every page of a project. Setting identity_provider to ldap, oidc or saml turns it into a multi-user knowledge base in which every search, page, tree, graph and RAG context is filtered by the permissions of the person asking — the same corporate permissions they have in Active Directory, the identity provider, or the source system itself. This part explains the model and the procedures; the open problems and the production checklist live in documentation.md (Italian) at the repository root.

9.1 How filtering works

  • Principals. A signed-in user carries a set of principals: application roles mapped from directory groups (identity_role_map), their personal principal user:<id> (AD objectGUID, OIDC oid/sub), and a clearance level. The role admin sees everything and may manage ACLs.
  • Labels on knowledge. Every document (source, meeting, synthesis) references an ACL key shared by all documents with the same rules: its own principals (acl_roles), a classification (public < internal < confidential < restricted), clauses read from the source system, and — for syntheses — the documents it derives from. Chunks inherit the key of their document, so filtering is done once per key, not per chunk.
  • Collections and gate. A collection gives principals and a classification to whole sources (an import branch or a folder) in one place, stored in the versioned acl.json. The project gate decides who may see the project at all; a hidden project answers 404, not 403.
  • Rules. Clauses are combined with AND, principals inside a clause with OR. A document without any label is visible only to admins (default-deny) once acl enforce on is set for the project; enforcement is off by default so an existing installation behaves exactly as before until you opt in.
  • Everything is filtered. Search, /wiki/tree, /wiki/page, the graph, index.md (generated per user), the project list, history and POST /rag/context — the endpoint LLM clients use to get context — all apply the same check.

9.2 Choosing an identity provider

ProviderLogin, roles, revocation
ldapUsername + password, once per session. Roles from group membership (nested groups included). Revocation: directory change detection; disabled accounts end their sessions.
oidcBrowser SSO (Entra ID, Okta, Keycloak, Google). Roles from the groups/app-roles claim, re-read with the refresh token at every cache expiry; an IdP refusal ends the session.
saml, roles from ldapBrowser SSO (AD FS, Entra ID, Okta, Shibboleth); roles and revocation exactly as with ldap. Recommended SAML setup.
saml, roles from the assertionBrowser SSO; roles from the assertion's groups attribute, fixed until the session expires (session_max_hours): SAML has no refresh.

  "ldap_bind_dn": "cn=svc-wikibridge,ou=service,dc=corp,dc=local",

OIDC needs oidc_issuer, oidc_client_id and usually oidc_groups_claim: "roles", oidc_user_id_claim: "oid". SAML needs pip install "wikibridge[saml]" and either saml_idp_metadata (https URL or file) or saml_idp_entity_id + saml_idp_sso_url + saml_idp_cert; register the metadata served at GET /identity/saml/metadata in the IdP. SAML verifies the assertion signature (SHA-1 rejected), recipient, audience, validity window and InResponseTo against a single-use request; IdP-initiated logins, encrypted assertions and Single Logout are not supported.

Security — with an identity provider and a non-loopback api_host the server refuses to start without TLS (api_tls_cert/api_tls_key or behind_tls_proxy: true). LDAP over plain ldap:// is refused unless StartTLS is on. Anyone who can read data/ on disk bypasses every ACL: the server warns at startup if the folder is readable by broad groups (GET /identity/status → deployment_warnings).

9.3 Sessions, the application key, real-time changes

  • Two separate headers: X-Wikibridge-Key identifies the client application (api_auth_token); Authorization: Bearer <session> identifies the user. A session comes from POST /identity/login (LDAP) or from the SSO flow (/identity/oidc/login, /identity/saml/login with a return_to on loopback or in oidc_return_urls/saml_return_urls).
  • Sessions are opaque, kept hashed in memory, and expire after session_idle_min (30) of inactivity or session_max_hours (8). Failed logins are throttled per user and per IP (login_max_failures_user 5 — keep it below the AD lockout threshold).
  • Roles are cached for entitlement_cache_ttl_s (300 s), so searches never wait for the directory. To apply a change sooner: the user calls POST /identity/refresh; an admin calls POST /identity/sync-groups (detects directory changes and clears the cache) or POST /identity/invalidate; or set ldap_change_poll_s to let the server check by itself.
  • A directory that cannot be reached yields 503 (nobody is logged out); an account removed or disabled yields 401 and all its sessions are revoked.

9.4 Labelling knowledge

# who may see the project at all (empty = everyone signed in)
wikibridge acl gate --role dipendenti --yes

# a whole import branch or folder, in one place
wikibridge acl collection legal-space --source imp-0003 \
    --role team-legal --classification confidential

# one document, including single persons
wikibridge acl page sources/contratto-acme.md --role team-legal --user mario.rossi

# review, then switch filtering on
wikibridge acl show
wikibridge acl enforce on

Changes that widen access are previewed and require --yes on the CLI or confirm: true over HTTP (every ACL endpoint also accepts dry_run). Widening means: new principals; a lower classification; sources removed from a collection; deleting a collection or emptying the gate; removing all of a document's own principals (the collection alone then decides); and turning the filter off (acl enforce off --yes). Narrowing never asks. Every ACL change, including acl enforce, is written to the audit log. Personal principals are resolved through the directory (--user), never typed as raw ids. Their readable names ("Mario Rossi (mario)") are kept in acl.json under labels for display only; decisions always use user:<id>.

From the GUI. In callAPIcall's Knowledge section an administrator gets a Permissions tab (filter on/off, who can open the project, collections with their sources, roles, people and classification). The Wiki view gains a Document permissions panel: collection and source-read rules are shown read-only, and the document's own rules can be edited. Widening changes show the same preview inline before Confirm and save. Roles are suggested from identity_role_map, source_group_map and the roles already in use (GET /acl → known_roles).

9.5 Permissions read from the source

  • Confluence — wikibridge import <url> --permissions: read restrictions of the page and of all its ancestors (they accumulate in Confluence) become AND clauses. Confluence groups map to roles with source_group_map (or source_group_passthrough); users are found in the directory by e-mail/username or through source_user_map (needed on Confluence Cloud, which hides e-mails). Space permissions are not read: model them with a collection.
  • Windows files (NTFS) — wikibridge ingest <dir> --recursive --permissions (or update --path … --permissions, or "permissions": true for POST /ingest/dir and POST /update): the file's effective DACL, inheritance included, gives the readers. SYSTEM and Administrators are ignored; Everyone, Authenticated Users and Users must be mapped explicitly in source_group_map. Deny entries cannot be represented and make the file admin-only. Requires pywin32.
  • Fail-closed — unreadable permissions, unmapped groups and unknown users make the document admin-only (principal acl:nessuno) and are listed in the report (acl_unreadable, acl_unmapped). Every update re-reads permissions even when the content did not change.

9.6 Updates, chunks and version history

wikibridge sources                         # updatable sources: wiki branches, folders, files
wikibridge update                          # check every source of the project
wikibridge update --import imp-0003 --path "D:\specs\msa.pdf"
wikibridge update --all-projects           # for a scheduled task / cron
wikibridge history sources/msa.md          # versions of a document
wikibridge history sources/msa.md --at 2026-09-01T10:00
  • Nothing runs by itself: updates start only when called (CLI, POST /update, an agent or a scheduler). Change feeds (Confluence CQL, MediaWiki RecentChanges) limit the work to what changed.
  • Pages keep a stable doc_id, so an update rewrites the same page instead of creating a duplicate, even after a rename. Documents are indexed as chunks per heading section; only changed chunks are re-indexed and get a new version.
  • Superseded chunk versions are kept for history_retention_days (365) and can reconstruct a document at a past date — visible only to users who may see the document today.

9.7 Syntheses, meetings and RAG context

  • Syntheses (POST /syntheses, wikibridge synthesis) declare their source documents and are visible only to users who can see all of them, re-evaluated at every request.
  • Meetings saved by a non-admin (POST /meetings) are visible to the saver and to the recognised participants.
  • RAG context — POST /rag/context {project, query, participants?, unresolved?} returns the relevant chunks the caller may see. With participants it returns only what every participant may see (for live meetings); unrecognised participants restrict the context to public content, or are ignored with unresolved: "ignore".

9.8 Audit log

wikibridge audit --path sources/contratto-acme.md    # who viewed this document
wikibridge audit --user mario --since 2026-09-01
wikibridge audit --verify                            # hash-chain integrity

Logins, failed logins, document views, searches and every change are appended to monthly JSONL files in audit_dir (default data/audit/), chained by hash so that edits or deletions are detectable. Query text is stored as a keyed hash by default (audit_query_mode: hash|full|none); files older than audit_retention_months (12) are removed. Only admins can read it (GET /audit, GET /audit/verify).

9.10 callAPIcall integration

  • With knowledge_access: "auto", callAPIcall detects multi-user mode and stops giving the LLM a path to the wiki on disk: the copilot and the meeting summaries receive only the filtered chunks from /rag/context. If WikiBridge is unreachable the assistant gets no knowledge at all (fail-closed), never a fallback to the files.
  • The Control Center's Knowledge section shows a sign-in panel (username/password, or "Sign in with your work account" for OIDC/SAML) and, once signed in, a “Viewing knowledge as …” bar with name, clearance and roles. The session is one per app and shared with the assistant, so what the operator sees and what the LLM receives go through the same filter.
  • Administrators manage permissions from the same section (§9.4, From the GUI); other users never see those controls.
  • Add the webview origin (http://tauri.localhost on Windows) to cors_origins; otherwise the GUI reports that WikiBridge refuses its requests.
